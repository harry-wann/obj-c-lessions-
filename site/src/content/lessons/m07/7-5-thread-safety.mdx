## Objective-C 怎麼寫

### 什麼叫執行緒安全

<Term en="thread safety" tw="執行緒安全" cn="线程安全" jp="スレッドセーフ" />：多條執行緒同時呼叫，結果仍然正確、不會 crash。Foundation 的規則很簡單：**不可變物件（`NSArray`、`NSString`、`NSNumber`……）執行緒安全，可變物件（`NSMutableArray`、`NSMutableDictionary`、`NSMutableString`……）一律不安全。** 兩條執行緒同時對 `NSMutableArray` 做 `addObject:`，內部的容量擴充與元素搬移互相踩到，結果是 `EXC_BAD_ACCESS` 或 `malloc: *** error for object: pointer being freed was not allocated`，而且只有偶爾發生。這也是為什麼 `LBLedger` 從 3.x 開始對外只回不可變的快照：快照拿出去之後怎麼讀都安全。

### `atomic` 不等於執行緒安全

```objc
@property (atomic, strong) NSMutableArray *items;    // 屬性預設就是 atomic
```

<Term en="atomic" tw="原子的" cn="原子的" jp="アトミック" />保證的只有一件事：**單次** getter 或 setter 是完整的。兩條執行緒同時 `self.items = newArray`，不會拿到一半舊一半新的指標，也不會因為舊值被提前釋放而 crash。就這樣。它**不保證**：

- `[self.items addObject:x]`：getter 是原子的，拿到指標之後對陣列做的事不在保護範圍。
- `self.count = self.count + 1`：讀跟寫是兩次原子操作，中間可以被插隊，兩條執行緒各加一可能只加了一。
- 「先檢查再動作」：`if (self.items.count > 0) [self.items removeLastObject];` 檢查完到動作前陣列可能已經空了。

所以實務上幾乎所有屬性都寫 `nonatomic`（省掉自旋鎖的成本），真的要執行緒安全就用下面的工具保護**整個操作**，而不是靠 `atomic`。Java 的 `AtomicInteger.incrementAndGet()` 之所以安全是因為它把「讀改寫」包成一個原子操作，ObjC 的 `atomic` 屬性沒有這種東西。

### 工具一：串列佇列保護狀態（actor 的前身）

```objc
@implementation LBLedger {
    dispatch_queue_t _queue;
    NSMutableArray<LBTransaction *> *_transactions;   // 只在 _queue 上碰
}
- (instancetype)init {
    if (self = [super init]) {
        _queue = dispatch_queue_create("com.littlebook.ledger", DISPATCH_QUEUE_SERIAL);
        _transactions = [NSMutableArray array];
    }
    return self;
}
- (void)addTransaction:(LBTransaction *)tx {
    dispatch_async(_queue, ^{ [self->_transactions addObject:tx]; });      // 寫：丟了就走
}
- (NSArray<LBTransaction *> *)transactions {
    __block NSArray *snapshot;
    dispatch_sync(_queue, ^{ snapshot = [self->_transactions copy]; });    // 讀：等結果
    return snapshot;
}
@end
```

原則：**共享狀態只在一條串列佇列上碰**，所有讀寫都是丟到那條佇列上的 block。串列佇列一次只跑一個 block，所以<Term en="critical section" tw="臨界區" cn="临界区" jp="クリティカルセクション" />（碰共享狀態的那段程式）天然互斥。寫用 `dispatch_async` 不等；讀要結果，用 `dispatch_sync` 等。這就是 Swift `actor` 做的事：actor 內部有一個串列執行器，`await ledger.add(tx)` 就是把呼叫排進去。差別是 Swift 編譯器會擋住你在外面直接碰 `transactions`，ObjC 靠的是你把 ivar 藏好、所有存取都走這條佇列的紀律。

### 工具二：並行佇列 + barrier 的讀寫鎖

串列佇列的缺點是讀也排隊：十個執行緒同時讀，九個在等。讀多寫少的資料（帳本正是）可以升級成<Term en="read-write lock" tw="讀寫鎖" cn="读写锁" jp="読み書きロック" />：讀可以同時、寫要獨佔。7.3 的 barrier 剛好就是這個：

```objc
_queue = dispatch_queue_create("com.littlebook.ledger", DISPATCH_QUEUE_CONCURRENT);

- (void)addTransaction:(LBTransaction *)tx {
    dispatch_barrier_async(_queue, ^{ [self->_transactions addObject:tx]; });   // 寫：barrier 獨佔
}
- (NSArray<LBTransaction *> *)transactions {
    __block NSArray *snapshot;
    dispatch_sync(_queue, ^{ snapshot = [self->_transactions copy]; });         // 讀：並行
    return snapshot;
}
```

只改兩個字：佇列型態改 `CONCURRENT`、寫入改 `dispatch_barrier_async`。讀取的 `dispatch_sync` 不變，多個讀可以同時在佇列上跑；barrier 來的時候等所有進行中的讀結束、獨佔執行、結束後讀才繼續。這就是 M07 第三個 xcode 題的全部內容，對應 Java 的 `ReentrantReadWriteLock`。

### 工具三：`@synchronized` 與它的代價

```objc
- (void)addTransaction:(LBTransaction *)tx {
    @synchronized (self) {                     // 以 self 當鎖
        [_transactions addObject:tx];
    }
}
```

`@synchronized (obj) { ... }` 是語言內建的<Term en="mutex" tw="互斥鎖" cn="互斥锁" jp="ミューテックス" />：同一時間只有一條執行緒能進入以同一個 `obj` 當鎖的區塊。對照 Java 的 `synchronized (this)`，連語法都一樣。它方便，但有三個代價：

1. **慢。** runtime 要用 `obj` 的位址去一張全域雜湊表查對應的鎖，再加上它是可重入鎖（同一條執行緒可以重複進入），比 `os_unfair_lock` 慢好幾倍。10.x 的 `LBLockBenchmark` 會量給你看。
2. **隱含 `@try / @finally`。** 為了確保例外飛過時鎖會釋放，編譯器把區塊包進例外處理，這在 7.2 說過有額外成本。
3. **鎖的粒度綁在物件上。** 用 `self` 當鎖等於整個物件一把鎖，任何人都可以在外面 `@synchronized (ledger)` 跟你搶同一把；用 `nil` 當鎖則什麼都不鎖、也不報錯。

結論：**偶爾進入、幾行就出來的小臨界區**（懶初始化、計數器）用 `@synchronized` 很好讀；高頻、要讀寫分離的狀態用佇列。`NSLock`、`os_unfair_lock`、`pthread_mutex` 等更底層的鎖留到 10.x 一起比。

### 主執行緒才能碰 UI

UIKit 不是執行緒安全的，而且它的規則比「上鎖」更嚴：**所有 UIKit 物件只能在主執行緒存取**。這不是慣例，是 Core Animation 的 layer tree 與事件系統的設計前提。從背景執行緒設 `label.text`，可能沒事、可能畫面不更新、可能幾秒後在完全無關的地方 crash。所以任何背景工作的結尾都是一句：

```objc
dispatch_async(dispatch_get_main_queue(), ^{
    self.totalLabel.text = total.lb_currencyString;
});
```

Xcode 9 起的<Term en="Main Thread Checker" tw="主執行緒檢查器" cn="主线程检查器" jp="メインスレッドチェッカー" />（Scheme → Diagnostics，預設開啟）會在偵錯時攔下背景執行緒上的 UIKit 呼叫，印出紫色警告並暫停在那一行；本章 crash 現場就是它。另一個偵錯工具 Thread Sanitizer（同一個面板）能抓到資料競爭本身，開著跑一次測試能省很多猜測，10.x 會要求 TSan 零警告。

### 完整範例（可貼進 Scratch）

```objc
#import <Foundation/Foundation.h>

@interface LBCounter : NSObject
- (void)bump;
- (NSUInteger)value;
@end

// 不安全版：atomic 屬性 + 多執行緒 ++
@interface LBAtomicCounter : LBCounter
@property (atomic, assign) NSUInteger count;
@end
@implementation LBAtomicCounter
- (void)bump { self.count = self.count + 1; }        // 讀、加、寫三步，中間會被插隊
- (NSUInteger)value { return self.count; }
@end

// 安全版：串列佇列
@interface LBQueueCounter : LBCounter
@end
@implementation LBQueueCounter { dispatch_queue_t _q; NSUInteger _count; }
- (instancetype)init {
    if (self = [super init]) _q = dispatch_queue_create("counter", DISPATCH_QUEUE_SERIAL);
    return self;
}
- (void)bump { dispatch_async(_q, ^{ self->_count++; }); }
- (NSUInteger)value { __block NSUInteger v; dispatch_sync(_q, ^{ v = self->_count; }); return v; }
@end

// 安全版：@synchronized
@interface LBLockCounter : LBCounter
@end
@implementation LBLockCounter { NSUInteger _count; }
- (void)bump { @synchronized (self) { _count++; } }
- (NSUInteger)value { @synchronized (self) { return _count; } }
@end

static void run(LBCounter *c, NSString *name) {
    dispatch_apply(10000, dispatch_get_global_queue(QOS_CLASS_USER_INITIATED, 0), ^(size_t i) {
        [c bump];                                      // 10000 次，多執行緒並行
    });
    NSLog(@"%@：%lu", name, (unsigned long)c.value);
}

int main(void) {
    @autoreleasepool {
        run([LBAtomicCounter new], @"atomic");
        run([LBQueueCounter new],  @"serial queue");
        run([LBLockCounter new],   @"@synchronized");
    }
    return 0;
}
// 預期輸出（atomic 那行每次不同、小於 10000）：
// atomic：9871
// serial queue：10000
// @synchronized：10000
```

`dispatch_apply` 是 GCD 的平行 for 迴圈，會用多條執行緒同時跑 block，是製造資料競爭最方便的工具。第一行少掉的那一百多次就是被插隊吃掉的 `++`。把 `LBAtomicCounter` 的 `count` 改成 `NSMutableArray` 做 `addObject:`，結果就不是少算而是 crash。

<Tip title="Swift actor 怎麼對應回來">
`actor` ≈ 串列佇列 + 藏好的 ivar；`await actor.method()` ≈ `dispatch_async` 丟進去（有回傳值則 ≈ `dispatch_sync`）；`@MainActor` ≈ 「這個類別的所有東西都要 `dispatch_async(main)`」；`nonisolated` ≈ 不碰狀態、不用進佇列的方法。12.x 混編時，ObjC 這邊用串列佇列保護的類別，Swift 那邊可以放心標成 `@unchecked Sendable`。
</Tip>

## 小結

- 不可變物件執行緒安全，可變集合一律不安全；同時 `addObject:` 是隨機 crash。
- `atomic` 只保證**單次** getter / setter 完整，不保護「取出後的操作」「讀改寫」「先檢查再動作」；實務上幾乎都寫 `nonatomic`，用別的工具保護整個操作。
- 保護共享狀態的三個工具：**串列佇列**（寫 async、讀 sync，Swift actor 的前身）、**並行佇列 + barrier**（讀並行、寫獨佔，讀寫鎖）、**`@synchronized`**（方便、慢、鎖綁物件，小臨界區用）。
- 在保護佇列上的程式直接碰 ivar，別再 `dispatch_sync` 回同一條佇列。
- UIKit 只能在主執行緒碰；背景回呼結尾 `dispatch_async(main)`。Main Thread Checker 與 Thread Sanitizer 都在 Scheme → Diagnostics。
