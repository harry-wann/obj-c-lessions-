## Objective-C 怎麼寫

### 第零步：先補測試

沒有測試的重構叫改寫，改寫壞了沒人知道。但舊專案多半沒有測試、而且**結構上很難測**（VC 裡直接呼叫 Singleton 與網路）。這時先寫<Term en="characterization test" tw="特徵測試" cn="特征测试" jp="特性テスト" />：不管行為對不對，先把「現在是怎樣」釘住。

```objc
// LBLegacyRateServiceCharacterizationTests.m
// 目的：釘住現有行為，不評價它對不對
- (void)testParsesLegacyJSONShape {
    NSData *fixture = [self dataFromFixture:@"rates-2016.json"];   // 從舊伺服器抓的真實回應存檔
    NSDictionary *rates = [LBLegacyRateService parseRates:fixture];
    // 第一次先寫 XCTAssertEqualObjects(rates, nil)，跑一次看它印出什麼，再把實際值貼進來
    XCTAssertEqualObjects(rates[@"USD"], [NSDecimalNumber decimalNumberWithString:@"0.0312"]);
    XCTAssertEqual(rates.count, 5);
}
```

三層測試依成本排：(1) **純函式的單元測試**——解析、格式化、計算；舊碼裡能拆出來的先拆（`+parseRates:` 從 delegate 方法裡抽成類別方法，不改邏輯）。(2) **特徵測試**——用真實的 fixture 餵進去、把輸出釘住。(3) **UI 煙霧測試**——XCUITest 開 App、點三個主要畫面、不 crash 就過。有 (1)(2) 保護的檔案才動；只有 (3) 的檔案只做機械式轉換（Convert to ARC、API 替換）。

### 小步 ARC 轉換：一檔一 commit

11.1 的 Steps 教過操作，這裡講策略：

1. **順序**：從葉節點開始——沒有被其他 MRC 檔案「擁有」的模型類別（`LBLegacyTransaction`）先轉，再轉持有它們的（`LBLegacyLedger`），VC 最後。這樣每次轉的檔案，它所持有的東西已經在 ARC 下，擁有權只有一個方向要想。
2. **每檔一 commit**，訊息固定格式 `ARC: LBLegacyTransaction`，方便 `git bisect`。
3. **轉完立刻跑 Zombie Objects 一輪**：工具會把 over-release 跟少 retain 一起「抹平」，原本在 MRC 下會 crash 的 bug 可能變成 ARC 下的洩漏（或反過來，原本靠 over-release 「平衡」掉的洩漏現在變 crash）。Memory Graph Debugger 看一眼轉換前後的物件數。
4. **`assign` 的物件屬性逐一決定**：delegate → `weak`；指向父物件的 back-pointer → `weak`；指向 `NSTimer` / `CADisplayLink` 這種會強持有 target 的 → 轉完要補 `invalidate`；真的需要不歸零的 → `unsafe_unretained`（幾乎不會）。
5. 全部轉完才拿掉 target 上剩下的 `-fno-objc-arc`，並把 `CLANG_ENABLE_OBJC_ARC = YES` 寫進 xcconfig。

### 逐步替換淘汰 API

11.2 的對照表決定順序（拒收 → crash → 風格）。每一類替換都是「**包一層 → 全部改呼叫新介面 → 刪舊實作**」，也就是<Term en="strangler fig pattern" tw="絞殺者模式" cn="绞杀者模式" jp="ストラングラーパターン" />：

```objc
// 第一步：包一層。LBAlert 內部還是 UIAlertView，但介面已是 block
@interface LBAlert : NSObject
+ (void)confirm:(NSString *)title
         inVC:(UIViewController *)vc
    onConfirm:(dispatch_block_t)onConfirm;
@end

// 第二步：全專案 UIAlertView 的 20 處呼叫改成 [LBAlert confirm:...]（純機械，可分多個 PR）
// 第三步：LBAlert 內部換成 UIAlertController，一個檔案，一個 PR，一次測完
```

好處是第二步的每個 PR 都不改行為，審起來快；第三步改行為但只有一個檔案。`NSURLConnection` → `NSURLSession`（本模組的 Xcode 任務）同理：先讓 `LBLegacyRateService` 對外變成 completion 介面、delegate 版留在裡面；呼叫端全改完後，再把內部換成 `NSURLSession`。

### 把一個 VC 改寫成 Swift

這是 12.x 的主題，這裡先給流程，讓你知道 11.x 做的每一步都在為它鋪路：

<Steps title="ObjC VC → Swift，六步">
<ol>
<li><strong>補 nullability</strong>（下一節）：VC 用到的每個 ObjC 標頭先包 <code>NS_ASSUME_NONNULL_BEGIN</code> / <code>END</code>，個別標 <code>nullable</code>。沒做這步，Swift 端每個 ObjC 回傳值都是 <code>!</code>。</li>
<li><strong>把相依性拉成 init 參數</strong>：VC 裡的 <code>[LBLegacyLedgerManager sharedManager]</code> 改成 <code>initWithLedger:</code> 注入。Swift 端才有辦法在測試裡換掉它。</li>
<li><strong>先轉模型與 service，再轉 VC</strong>：跟 ARC 轉換一樣從葉節點開始。Swift 類別要給 ObjC 用就加 <code>@objc</code> 並繼承 <code>NSObject</code>，Xcode 會產生 <code>LittleBook-Swift.h</code>。</li>
<li><strong>新 Swift 檔與舊 ObjC 檔並存一個版本</strong>：用 feature flag 或 <code>#if</code> 切換，上線觀察 crash 率。</li>
<li><strong>刪 ObjC 版</strong>，從 storyboard / 路由表 / 橋接標頭移除參考。</li>
<li><strong>更新 ONBOARDING.md</strong>，標記哪些模組已是 Swift。</li>
</ol>
</Steps>

### 補 nullability 標注

<Term en="nullability annotation" tw="可為空性標注" cn="可空性注解" jp="Null 許容性アノテーション" />只在標頭檔，不改行為，是遷移的第一個安全步驟。原則：**整個標頭包起來、個別標 nullable**。

```objc
// LBLedger.h
NS_ASSUME_NONNULL_BEGIN

@interface LBLedger : NSObject
@property (nonatomic, copy, readonly) NSArray<LBTransaction *> *transactions;  // 隱含 nonnull
- (nullable LBTransaction *)transactionWithIdentifier:(NSString *)identifier;   // 可能找不到
- (void)addTransaction:(LBTransaction *)transaction;
- (BOOL)removeTransactionWithIdentifier:(NSString *)identifier
                                  error:(NSError * _Nullable * _Nullable)error;  // 雙重指標要寫完整
@end

NS_ASSUME_NONNULL_END
```

補標注的方法：對每個回傳指標的方法問「實作裡有沒有任何路徑 `return nil`？」有就 `nullable`。對每個參數問「實作有沒有處理 nil？」沒有就讓它維持 nonnull（Swift 端會被擋住，ObjC 端傳 nil 會有警告）。M12 的 `testNullabilityAnnotationsPresent` 會檢查主要標頭都有 `NS_ASSUME_NONNULL_BEGIN`。

標注之後編譯器會開始警告 `null passed to a callee that requires a non-null argument`，每一個警告都是一個以前沒發現的潛在 nil 傳遞——**不要為了消警告把所有東西標成 nullable**，那等於沒標。

### 什麼時候不要重構

<Term en="technical debt" tw="技術債" cn="技术债" jp="技術的負債" /> 不是全部都要還。不要動的情況：

- **沒有測試保護、而且你半年內不會再碰它**：穩定跑了五年的 MRC 檔案，`-fno-objc-arc` 留著，不會因為「它很舊」就壞。
- **三個月內要下架或重寫的模組**：遷移成本回收不了。
- **行為沒人說得清楚的程式碼**：先寫特徵測試把它釘住，釘不住就不要碰。
- **PR 同時改行為又改結構**：把「搬家」跟「裝修」拆成兩個 PR；審查者一次只能看懂一種 diff。
- **為了用新語法而改**：`objectForKey:` → `dict[@"x"]`、`@synthesize` 刪除，這類只在順手經過時改，不開專門的 PR 洗整個專案（會讓 `git blame` 全部變成你）。

判斷句：**這次重構省下的，是不是下一次改這段程式碼時會花掉的時間？** 答不出下一次是什麼時候，就不要重構。

<Tip title="每個 PR 只做一件事，而且是可逆的">
ARC 轉換一檔、API 替換一類、nullability 一個標頭、Swift 改寫一個 VC。每個 PR 都要能 `git revert` 而不牽動別人。這比「重構得多漂亮」重要十倍：接手舊專案最大的風險不是技術，是沒有人能在壞掉時找出是哪一步壞的。
</Tip>

<Pitfall title="為了消警告把所有東西標 nullable">
<Fragment slot="bad">
```objc
- (nullable NSArray *)transactions;          // 其實永遠回傳非 nil 陣列
- (void)addTransaction:(nullable LBTransaction *)tx;   // 其實傳 nil 會 crash
// Swift 端：每一行都要 if let / guard let，而且仍然不安全
```
</Fragment>
<Fragment slot="good">
```objc
NS_ASSUME_NONNULL_BEGIN
- (NSArray<LBTransaction *> *)transactions;  // 回傳空陣列而非 nil（1.x 的慣例）
- (void)addTransaction:(LBTransaction *)tx;  // nil 進來編譯器警告
- (nullable LBTransaction *)transactionWithIdentifier:(NSString *)identifier;
NS_ASSUME_NONNULL_END
```
</Fragment>
標注是**承諾**：`nonnull` 承諾實作不回 nil，`nullable` 承諾呼叫端會處理。全部 nullable 等於不承諾任何事，Swift 端的 `?` 滿天飛，遷移的價值沒了。
</Pitfall>

<Pitfall title="搬家跟裝修放同一個 PR">
把 `LBLegacyListViewController` 從 MRC 轉 ARC、順便把 `UIAlertView` 換掉、順便抽一個 view model、順便改用 `NSURLSession`，一個 PR 2000 行。審查者看不懂、CI 紅了不知道是哪一步、revert 會連帶退掉三件正確的事。四件事四個 PR，每個都能獨立 merge 與 revert。
</Pitfall>

<Crash message={`Fatal error: Unexpectedly found nil while implicitly unwrapping an Optional value
// StatsViewController.swift:42
let tx = ledger.transaction(withIdentifier: id)   // ObjC 標頭沒標 nullability
label.text = tx.note                               // tx 的型別是 LBTransaction!`}>
這是 Swift 端的 crash，但根因在 ObjC 標頭：`transactionWithIdentifier:` 沒有 nullability 標注，Swift 把回傳值匯入成 `LBTransaction!`（隱含解包的 Optional）。呼叫端寫起來跟非 Optional 一樣，找不到交易時 ObjC 回 nil，`tx.note` 那一行直接 fatal。

修法在 ObjC 端：標頭加 `- (nullable LBTransaction *)transactionWithIdentifier:`，重新編譯後 Swift 端那行會變成編譯錯誤 `value of optional type 'LBTransaction?' must be unwrapped`，逼你寫 `guard let`。這就是「先補 nullability 再改 Swift」的順序為什麼不能反：沒標注的 ObjC API 在 Swift 裡每一個回傳值都是地雷，而且編譯器幫不了你。
</Crash>

## 小結

- 動舊碼之前先補測試：能拆的純函式寫單元測試；拆不開的用 fixture 寫特徵測試釘住現狀；只有煙霧測試的檔案只做機械式轉換。
- ARC 轉換從葉節點開始、一檔一 commit、轉完跑 Zombie 與 Memory Graph；`assign` 物件屬性逐一決定 `weak`。
- 淘汰 API 用絞殺者模式：包一層 → 改呼叫端 → 換內部；順序看拒收、crash、風格。
- ObjC → Swift 六步：nullability → 注入相依 → 先模型後 VC → 並存觀察 → 刪舊版 → 更新文件；標注用 `NS_ASSUME_NONNULL` 包整檔、個別 `nullable`，不要全標 nullable。
- 不要重構：沒測試又不會再碰、三個月內下架、行為釘不住、搬家與裝修混在一個 PR、純語法洗版。
